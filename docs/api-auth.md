# Sanctum Authentication API

Laravel is the business backend; Filament is an administration and monitoring
surface only. Application users authenticate through `/api/v1` and cannot enter
Filament unless an administrator explicitly grants both an admin role and
`panel.access`.

## Credential modes

| Client | Credential | Recommended storage |
| --- | --- | --- |
| First-party Nuxt | Sanctum stateful session + CSRF | Laravel `HttpOnly` session cookie |
| iOS / Android | 15-minute access token + rotating refresh token | Keychain / Keystore |
| Legacy integration | Expiring Sanctum personal access token | Server-side secret store |

All protected business endpoints use `auth:sanctum`, so the same endpoint can
accept either a trusted Nuxt session or a Bearer access token. Authorization for
business features must still use Laravel policies/permissions, not token
abilities alone.

Private modules use
`Douwyn\StarterKit\Platform::API_AUTHENTICATED_MIDDLEWARE` instead of copying
the host middleware classes. The `starter-kit.api-authenticated` group includes
API locale selection, `auth:sanctum`, active-account enforcement, and browser
session tracking. A directly loaded package route file must additionally apply
Laravel's `api` middleware group.

## Nuxt stateful session

Before a mutating request, the browser obtains a CSRF cookie:

```http
GET /sanctum/csrf-cookie
Accept: application/json
X-Requested-With: XMLHttpRequest
```

It then sends `credentials: include` and the decoded `XSRF-TOKEN` value in
`X-XSRF-TOKEN`.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/auth/session/register` | Register and create a browser session |
| `POST` | `/api/v1/auth/session/login` | Log in without issuing a PAT |
| `POST` | `/api/v1/auth/session/challenges/verify` | Finish a session-bound 2FA challenge |
| `POST` | `/api/v1/auth/session/logout` | End only the current browser session |

Session endpoints accept only exact origins configured by both
`SANCTUM_STATEFUL_DOMAINS` and `CORS_ALLOWED_ORIGINS`. Login and challenge
verification remain CSRF-protected.

## Mobile token family

Canonical mobile register/login requires:

```json
{
  "email": "user@example.com",
  "password": "Secret123",
  "device_name": "Jane's iPhone",
  "device_id": "57ad0a3b-b745-4475-bdea-b8c85bdeb8e4",
  "platform": "ios",
  "app_version": "1.4.0"
}
```

`device_id` is an installation UUID generated by the app. Laravel stores only
an HMAC fingerprint of it.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/auth/token/register` | Register and issue a mobile token pair |
| `POST` | `/api/v1/auth/token/login` | Log in and issue a mobile token pair |
| `POST` | `/api/v1/auth/token/challenges/verify` | Finish a mobile/legacy 2FA challenge |
| `POST` | `/api/v1/auth/token/refresh` | Rotate both tokens |
| `POST` | `/api/v1/auth/token/logout` | Revoke the device family using its refresh token |

Successful login, registration and refresh return raw credentials once:

```json
{
  "data": {
    "user": {},
    "access_token": "12|douwyn_...",
    "token_type": "Bearer",
    "expires_in": 900,
    "expires_at": "2026-07-11T10:15:00Z",
    "refresh_token": "019...|douwyn_rt_...",
    "refresh_expires_at": "2026-08-10T10:00:00Z",
    "device_session_id": "019..."
  }
}
```

Every refresh request includes a UUID `request_id`. The app must reuse that ID
when retrying the same request after a timeout, and atomically replace both
stored credentials after a successful response. Laravel persists an
application-key-encrypted replay envelope in the same database transaction as
the rotation, then uses the shared cache lock as a fast path. The envelope is
eligible for deletion after 60 seconds, so a lost response can be replayed
safely even after a cache miss or process restart without looking like token
theft.

Reusing an already-rotated refresh token revokes the complete device family and
requires a new login. Raw access tokens, refresh secrets and device IDs are not
stored in plaintext or written to the activity log. The database keeps token
hashes plus the short-lived encrypted replay envelope described above.

`/api/v1/auth/register` and `/api/v1/auth/login` can be enabled temporarily for
legacy clients with `AUTH_LEGACY_TOKEN_ENDPOINTS=true`; they are disabled by
default because they bypass device-family rotation. Canonical `/token/*`
registration and login always require `device_id` and `platform` and always
return the rotating mobile contract.

## Two-factor challenge

A valid login for an account with 2FA returns HTTP `202` and no credential:

```json
{
  "code": "two_factor_required",
  "data": {
    "challenge_token": "douwyn_ch_...",
    "method": "app",
    "recovery_available": true,
    "expires_at": "2026-07-11T10:05:00Z"
  }
}
```

Verify it using exactly one of `otp` or `recovery_code`. The password is not
sent again. Challenge secrets are opaque, stored only as SHA-256 hashes, expire
after five minutes, allow at most five failed attempts and are invalidated when
the password or 2FA state changes. Nuxt challenges are additionally bound to
the pre-auth browser session; mobile device metadata is sealed into the
challenge and cannot be replaced during verification. Mobile verification must
also resend the installation `device_id`; Laravel compares its HMAC with the
value sealed into the challenge before issuing the access token.

## Account and security endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/auth/me` | Current user/profile |
| `PATCH` | `/api/v1/auth/me` | Update profile |
| `PUT` | `/api/v1/auth/password` | Change password and revoke other access |
| `GET` | `/api/v1/auth/tokens` | List legacy/PAT access tokens |
| `DELETE` | `/api/v1/auth/tokens/{id}` | Revoke an owned PAT |
| `GET` | `/api/v1/auth/devices` | List owned mobile device families |
| `DELETE` | `/api/v1/auth/devices/{id}` | Revoke one owned mobile device |
| `DELETE` | `/api/v1/auth/devices` | Revoke all owned mobile devices |
| `GET` | `/api/v1/account/security/sessions` | List active browser sessions using opaque IDs |
| `DELETE` | `/api/v1/account/security/sessions/{id}` | Revoke one owned browser session |
| `DELETE` | `/api/v1/account/security/sessions/others` | Revoke browser sessions other than the current Nuxt session |
| `DELETE` | `/api/v1/account/security/sessions` | Revoke every browser session |

Raw Laravel session IDs and raw user-agent strings are never returned. A Nuxt
request that revokes its current/all browser sessions is logged out immediately;
a Bearer request can revoke browser sessions without revoking its own token.

Account Security lives at `/api/v1/account/security`:

- `GET /` returns 2FA status and recovery-code count without secrets.
- `POST /two-factor/app/setup` and `/app/confirm` use a pending TOTP secret.
- `POST /two-factor/email/setup`, `/email/resend` and `/email/confirm` manage
  email 2FA.
- `POST /two-factor/email/current-code` sends the current email step-up code.
- `DELETE /two-factor` disables 2FA.
- `POST /recovery-codes/regenerate` replaces recovery codes.

Sensitive changes require the current password and, when 2FA is active, either
the current OTP or a recovery code. Pending setup never replaces the working
factor before confirmation. Recovery codes are shown once and stored as hashes.

## Account lifecycle

The lifecycle contract works with a Nuxt Sanctum session or a mobile Bearer
token wherever authentication is required:

| Method | Endpoint | Authentication | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/email/verify` | Public opaque token | Verify the account's current email |
| `POST` | `/api/v1/auth/password/forgot` | Public | Send a reset link with an enumeration-safe response |
| `POST` | `/api/v1/auth/password/reset` | Public opaque token | Set a password and revoke all access |
| `GET` | `/api/v1/account/email` | Session or Bearer, `user:read` | Verification and pending-change status |
| `POST` | `/api/v1/account/email/verification-notification` | Session or Bearer, `user:update` | Replace and resend the verification token |
| `POST` | `/api/v1/account/email/change` | Session or Bearer, `user:update` | Start a verified email change |
| `POST` | `/api/v1/account/email/change/confirm` | Same authenticated user, `user:update` | Confirm the new address and revoke other access |

Email-change initiation requires a verified current address, the current
password, and the current OTP or a recovery code when 2FA is enabled. The new
address is normalized and checked case-insensitively both when issuing and
consuming the token. Confirmation preserves only the credential submitting it.

Laravel stores only a domain-separated token HMAC, an authentication-state
snapshot and an email snapshot. Raw values only enter the encrypted queued
notification. Reissuing consumes the predecessor; password reset revokes all
browser sessions, Sanctum tokens and mobile refresh families. Sensitive
lifecycle responses use `Cache-Control: no-store, private`. The public email
verification response is deliberately message-only and never returns a user
profile; an authenticated client can refresh `/auth/me` afterward.

```dotenv
FRONTEND_URL=https://app.example.com
AUTH_EMAIL_VERIFICATION_URL=https://app.example.com/auth/verify-email
AUTH_PASSWORD_RESET_URL=https://app.example.com/auth/reset-password
AUTH_EMAIL_CHANGE_URL=https://app.example.com/account/confirm-email-change
```

## Configuration and cleanup

```dotenv
AUTH_ACCESS_TOKEN_MINUTES=15
AUTH_REFRESH_IDLE_DAYS=30
AUTH_REFRESH_ABSOLUTE_DAYS=90
AUTH_REFRESH_REPLAY_SECONDS=60
AUTH_REFRESH_LOCK_SECONDS=30
```

Run Laravel Scheduler in production. It prunes expired Sanctum tokens, browser
sessions, OTPs, auth challenges, pending 2FA setups and retained mobile token
families. It also removes expired/consumed account-action tokens. A queue worker
is required for encrypted lifecycle email notifications.

Interactive Scramble documentation is available at `/admin/api-docs` only to
active `admin` or `super_admin` users with `panel.access`.

Platform 2 issues new credentials from the singleton
`TokenAbilityRegistry`. Its `legacy` profile defaults to `user:read` and
`user:update`; its `mobile` profile additionally includes `devices:read` and
`devices:revoke`. Modules may extend a profile during provider boot. The
resolved list is sealed into 2FA challenges and mobile device families, so
refresh rotation preserves the original list and never silently widens an
existing credential.

Authentication and account-security actions also emit structured audit events
for the permission-gated Filament dashboard. See
[Security telemetry](security-telemetry.md) for the event catalogue, sensitive
data rules, retention, and recommended alert hooks. API clients should use the
stable error codes and correlation headers documented in
[API lifecycle and errors](api-lifecycle.md).
